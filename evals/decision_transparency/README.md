# 决策透明度行为评估

这些都是虚构项目，不是实际业务验收。需要 Python 3.9+ 与 Git，无依赖安装。

1. `python3 -B evals/decision_transparency/setup.py /tmp/steward-behavior-new`。目标必须不存在；脚本创建九个项目和文件指纹，只在 C 创建独立本地 Git 基线，用虚构身份且禁用 Hook 和全局配置。
2. 每案使用一个不继承作者对话的新上下文，显式读取候选 `SKILL.md` 及所需引用，告知唯一项目根，并原样提供 `cases.json` 对应请求。不要提供预期答案。不读其他案例、真实项目，不联网或派发 Agent。
3. 将实际用户回应、同范围 Brief（不适用时说明）、真实读写/执行记录存入项目外单独获准的报告目录。F 只允许修改 validator.py 并运行指定测试；H2 只允许修改 README.md 的错字；其他案项目只读。不得用作者预写回应替代实际调用。
4. 比较 BASELINE.json 与结果文件；只读案不得产生项目改动。F 应真实修复并验证；H2 应只有指定错字差异。记录未运行项、失败和重试，不能编辑历史回应伪装通过。
5. 独立复核判断 A 轻量开工、B 原台账复用、C 现成 Git/测试与验收断点、D 实际并发/恢复控制、E 限定追问、F 授权内执行、G 暂缓不写入、H 不过度触发。检查推荐因果、较轻/较重方案、两层范围一致及证据状态；机械关键词不作行为通过依据。
6. 另一个新上下文仅看用户层回答五问：最需补什么、可复用什么、为何不用更轻/更重、批准什么、哪些以后再做。核对回答与实际方案。模型理解与真实人类新手试用分开，未开展后者标 not_run。

独立复核与最多两轮同范围返修须保留原记录；不换案例名清零。用户明确只读时，成功意味着诊断与待批准方案，不意味着工程机制已实施。

用户决策体验定向评估：复用 B/C/D/H2，使用新的隔离根、报告目录与无历史结论上下文。D 的盲读评估者只看用户报告，回答并逐项引用原句：批准会做什么、仍禁止什么、哪些实际结果才成功、哪些结果失败/须暂停、哪些可撤/不能保证恢复、较轻替代是否需确认不同范围。无法从原文支持则标不充分，不猜测 Brief。再由独立 Reviewer 对照原文和同范围 Brief 核对，不用字数或关键词代替理解与范围判断。小改 H2 须真实修改且不重复审批。新任务的独立授权与返修计数单独记录，旧版失败保持原样；实际调用、模型理解、人类试用分别报告。
