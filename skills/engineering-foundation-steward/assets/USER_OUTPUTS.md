# 工程基建决策：用户层与实施层

以下是回复结构，不要求新建同名文件、数据库或工作模式。适用于kickoff/retrofit准备创建、补强或显著升级工程基础。已有准确授权只报必要差异与结果；简单概念/普通小改直接处理，不套完整报告。完整虚构示例见[两层同方案](../examples/DECISION_REPORT_EXAMPLE.md)。

## A. 先让用户看懂决定

先给2～3句结论：这是什么阶段的项目，最重要的问题是什么，建议做什么；术语首次出现随句解释。不先摆十领域大表。用户层用中文能力/许可表述；函数名、实现语法、E编号和英文状态留工程层，必要术语随句解释。路径清单可保留，但不要让用户先读代码才理解选择。

**项目与本次范围。** 要完成什么、当前阶段、重要风险/复杂度、想让AI自主到哪一步；读了哪些来源，哪些未知。未知自主目标可写“本次先讨论/按已批准单任务”，不迫使用户先选A1/A2术语。

**现成的东西。** 只列影响判断的能力，用实际证据区分：已验证可用 / 有实现但未接入或未完整验证 / 仅文档 / 当前值得补 / 证据不足。新项目以已有资产和开工条件为主；不靠文件名缺失判缺能力。

**建议与理由。** 现在最重要1～3项，每项把以下因果链写成短段或简表：

|问题与条件|推荐及预期结果|为何是这个程度|不做与以后升级|
|---|---|---|---|
|真实来源是什么，谁会遇到哪种失败|复用什么，补哪种实际机制|较轻方案为何够/不够；较重方案现在多付什么成本、是否必要|保留哪项风险；出现哪个具体事件再复查|

再用短句列“具体变化后再做”和“当前不用做”。十大领域全覆盖表只在确有必要时附后，不代替上述结论。不要把“建议采用结构化管理”当作原因，也不把更多Markdown说成已落实代码保护。

**这次请你决定。** 用用户结果和影响表述，必要时比较推荐方案、适用替代、暂不做；没有实质替代不凑三选一。说清要写/运行的范围、数据/费用影响、谁实施、怎样验证和撤回。用户不用挑库或底层命令。只提出当前可批准的准确阶段，明确列出拟改路径或已有范围引用；缺前提的后续项单列，不能前文合并三项请批、末尾又暗中缩为两项。替代方案尚未形成准确Brief时注明“选择后收窄/重列范围”，不能套用推荐方案施工单。未批准写入时状态为proposed；已有批准则注明对应来源与适用范围，只有新增部分需决定。拒绝时说明仍可继续的安全工作与复查条件。

**批准后的结果与退出（直接写在用户层）。** 让用户不打开Brief也能决定；不能用“具体验收/停止/撤回见Brief”替代关键条件。按风险合并成短段，不强制所有项目填表：

- **会做 / 不会做：** 谁能改哪些文件、运行什么、碰什么数据、有无费用；实际施工/审核Agent与测试中模拟的提交者必须分开，准确阶段直说是否启动额外Agent，角色设想不隐含派发许可，两层一致；较轻替代若改变施工或测试范围，须先呈现对应范围让用户确认，不能沿用推荐方案许可。
- **怎样算成功：** 写出可观察的测试结果，不只说“测试通过”。高风险并发例：两个执行者同时提交旧版本，只能一个保存成功，另一明确收到冲突，文件仍完整；恢复例：用独立备份在另一位置还原，内容逐项一致。按本项目实际采用的控制选必要例子；试验副本通过不代表真实系统已接入。
- **怎样算失败、何时暂停：** 丢失他人更新、错误也返回成功、越界写入或无法恢复等判为失败；结果不明先停相关写入查事实，不盲目重试。说清已批准范围可修到哪里、何种变化需另批；用户叫停即停相关后续动作。不要把未知说成成功，也不冻结无关安全工作。
- **不满意或失败怎样退出：** 停止后续写入，保留错误证据；依修改前副本/差异只撤本次改动，遇他人后续改动先核对，不直接覆盖。说明哪些新增文件能停用、删除是否已获准。撤回代码不等于恢复已改数据；没有独立恢复证据就不保证数据恢复，已外发/收费等不能靠代码撤回。只说与本次实际风险有关的限制，不罗列无关灾难。

这是用户决定条件的完整性检查，不是加长报告的要求。低风险方案可用两三句话说清成功、暂停和撤回；普通小改不触发此报告。用户层省略无助决定的模式名和英文状态；文件名可保留，字段/函数先解释用途（如版本号revision、统一保存函数）。术语优先换成人话，必须保留时首次就地解释（如“锁：让保存操作排队，不会同时覆盖”；“符号链接：能跳转到另一位置的文件指针”，说明为什么禁止借它写出获准目录）。提交前暂时遮住Brief，检查用户能否仅凭用户层回答：会做什么、禁止什么、何种结果成功、何种情况失败/暂停、能撤什么/不能恢复什么、轻方案是否需确认不同范围；缺项补在用户层，技术命令与算法细节仍留Brief。

用户层不是删掉重要限制的摘要：不要把“已实现待测”写成“已可用”，不要隐藏安装、外部访问或真实数据风险。

## B. 给项目 Main 的同方案 Implementation Brief

沿用原 Brief，不另建任务系统。用相同建议名称或已有brief_id对应用户层每项决定；版本与范围有变化时两层一起更新。

- 结果、当前动作、现有事实源与版本：准确根/文件/证据及未查范围。
- 复用与控制：哪些保持、哪些需补，为什么足够。需要知识接续时，用短段说明保留内容、现有位置、读取时机、维护者与更新事件、证据/适用条件及失效复查；无此需要不填额外表。
- 精确拟改文件、工具/环境、运行/写入副作用和非目标。
- 涉及已有能力时：原调用行为、拟改变及兼容影响、消费/呈现入口；用户结果与同范围可执行链对应，不把未接通的底层结果当用户已能看到。
- 验证：正常与失败判据、命令/场景、版本绑定；运行未获准则写待执行，不伪报通过。
- 项目唯一写者、必要只读审核角色；不让Skill承担长期调度。
- 授权依据、普通返修边界、停止/升级条件；已有准确授权不重复要求批准。
- 撤回/恢复：只撤本次内容，保护原资产与后续他人改动，真实数据恢复须另验。
- 实施后复查：同一方案实际做了什么、验证了什么、未覆盖什么；何种变化再调用。

**两层核对：**目标、控制项、写入/运行范围、许可、费用和风险是否一致？任务表和收口中的状态/知识落盘也算写入，不能藏在“由 Main 维护”里；入口未知或只读时只交证据与待同步事项，明确且已批准的更新则沿用原许可。用户层可以概括文件职责，但不能隐藏新增施工；若不一致，先收窄工程层或补充用户选择，不先执行扩大范围。

采用JSON Brief时仍用原v2字段，status固定proposal_only表示草案；真实授权在项目来源中独立核实，不能把字段改成authorized来绕过批准。没有结构化合同输入时用原项目入口与Markdown Brief，不为跑校验器另造合同。

## C. 阶段草案与收口

Stage Charter沿用用户结果、非目标、起始版本、成果复用、依赖、准确动作、普通返修/停止条件和整体验收。它建议项目需要的执行基础，不是Skill接管调度。草案不是许可；已批准范围可由Main连续实施。

收口回到同一建议：assessed / proposed / authorized / implemented / verified_in_scope，并将partially_verified、blocked、unknown分别说清。能力状态与动作许可分列，已验证不等于人类Accepted。原项目维护事实，不建立本Skill的长期状态库。

## D. 可选接入说明

说明显式调用/项目路由/Hook或受控门的实际宿主、版本、范围、配置、信任、事件与Main实际行动。分别标not_requested / proposed / configured_untrusted / trusted_unobserved / observed / failed / disabled / unsupported。未安装不能说持续提醒有效；Hook不是报告或基建实施的前置。
