# 控制目录：匹配的是实际能力，不是文件数量

每个控制都回答：它防什么失败；什么事件需要它；最低实物/流程；怎样验；何时升级。E编号只用于追踪，用户不必记忆。

## E01 目标与需求

最低：一个用户结果、当前动作、非目标、可检查的成功条件。长期产品增加目标到里程碑到任务的关联。变更产品方向、用户类型或数据用途时复核。缺目标可讨论方案，不能自行假设真实产品范围并实施。

验证：用具体例子说明成功与失败；纯技术任务也说明它服务哪个产品或工程结果。

## E02 架构与边界

最低：模块职责、数据流、不可触碰区域。多个使用方或多服务需要接口和版本兼容；共享通用工具与业务适配分开维护。

验证：一个任务的拟改文件与职责相符；跨边界变更有明确依据。不要为了“模块化”过早拆服务。

## E03 版本控制与变更

最低：维护型代码尽早建立安全Git基线，确定根、分支、未提交资产、忽略和秘密策略。新目录也要检查父仓库/嵌套仓库/工作树，不能仅找`.git`目录。

验证：追踪范围和准确提交可核，测试对应正确版本；没有执行commit就不报已版本化。远端只在许可内核查，无法访问明确未知，本地远端缓存不冒充在线事实。

工程增强触发：多人或多分支合入时配置必要审核/状态检查；真实事件同步不靠手写摘要。检查配置本身也须测试。Git不是用户数据备份。

## E04 环境、依赖与执行

最低：已确认运行/验证命令、依赖版本、配置提供方式、秘密与虚构数据边界。只读扫描不能安装或执行项目脚本。

验证：依据授权在隔离场景运行最小检查；记录版本/环境/终态。多工作区需要隔离和资源控制；本地可运行不等于跨机器可重现。

## E05 任务与状态

最低：任务身份、目标、责任、状态、验收、下一步及阻塞。有既有平台优先复用。多写者或并发状态更新必须指定单一写入口或版本冲突检测，不接受“大家记得同步”作为已落实保护。

验证：目标→产物→真实证据→验收→状态→下一步可追溯。被授权的重复提交不能重复关闭/执行。状态转换条件和正式批准分开。

## E06 项目治理与阶段授权

最低：阶段结果、优先级、重大决定归属、异常升级。A2需明确继承任务边界和依赖任务可推进条件。

验证：任务都完成但用户结果失败时不能宣布阶段通过；预批普通工程纠错无需逐项请示，越界风险必须升级。规则修改不得只埋在某次报告里。

## E07 知识、决定和复用

最低：已有成果入口、有效决定和替代关系。重复开发/多使用方触发功能导航或结构化能力索引；现有模块说明足够时不重复造目录。

验证：面对已有功能需求先定位实现、版本、验证和连接状态。索引是导航/派生视图，不能另维护Accepted真相。候选、已验证、已采用分别表达。

## E08 质量、证据与审查

最低：成功标准、正常/错误路径检查、版本和范围绑定。需要多层测试时不能用样例截图替代。重要任务增加独立Review，但不把Reviewer当全知裁判。

验证：未运行为not_run，失败为failed，未知为unknown；测试被跳过要有原因。旧版本通过不替新版本，Hash一致不等于正确。范围内代码改动须有对应回归策略。

## E09 发布、数据恢复与资产生命周期

最低：可交付版本、重要数据的保护和恢复方法；涉及删除、覆盖、生产迁移时需先验证适当恢复。数据安全不限于项目体积。

验证：独立恢复证据；版本回退与数据恢复区分。依赖/缓存是否可重建，未决故障是否仍引用，运行现场是否仍活动，都要核实后才建议清理。日志限制体积、秘密脱敏、保留必要原件。

## E10 Agent执行与协作

最低：准确任务输入、工具权限、接手来源、停止和返修条件。A1验证任务闭环；A2验证多任务选择与阶段验收；A3另需真实调度和恢复机制。

验证：不把ACK当完成，不把交接当新权限；并发写入有控制；未知有副作用结果不能盲目重试。遇预算、撤销授权、规则冲突要停止依赖动作。

## 按动作选择启动线

| 当前动作 | 不应缺少的能力 |
|---|---|
| 方案讨论 | E01可讨论目标，明确假设；无需假装完整工程已就绪 |
| 只读体检 | E02根/范围与E10读取许可；秘密保护 |
| 隔离原型 | E01小目标、E03安全保存策略、E04虚构环境、E08样例验收 |
| 正式维护开发 | E03版本、E04验证、E05任务、E08检查、E10动作范围 |
| A2阶段推进 | 上项加E06阶段授权、E07复用、E05依赖更新、E10真实接续入口 |
| 真实数据操作 | 增强E02权限边界、E04隔离、E09恢复、E08风险验证 |
| 公网或多人发布 | 增强身份/安全/隐私、发布运行观测、恢复及相应专项检查 |
| 多Agent共同写状态 | E05受控写入/版本冲突与E10所有权必须实际落实 |

十领域不是安全合规全集。高影响领域应明确外部专家/规范依赖，但不因无关专业要求阻断普通材料阅读。

## 判断算法的要求

依据证据先确定已有能力，再判断当前动作所需控制。每个建议给触发原因、最小实现和验证；结果分 `now / later_when / not_needed_now`。later_when必须是具体事件，例如“第二名写者加入”，不是含糊的“未来”。

不设一个总分决定所有动作。一个关键数据恢复缺口不能被其他九项高分抵消；低风险文件编辑也不因发布备份未验而全部停下。

## 向用户解释选择，不能按项目体积套套餐

把E编号留在工程层。用户层先说风险与结果；第一次术语出现给一句具体解释，如“版本冲突检测：保存前比较你读取的版本，别人已更新就拒绝覆盖”。

- 简单无真实数据、单写者的小Skill：本地版本记录与代表性输入检查通常足够；不因名字是Skill就要求任务数据库。长期维护再补持续回归。
- 有既有研究登记和校验器：先证明哪些可复用；缺版本保护、可复跑验证或入口时定点补强，不另立研究状态真相。
- 多模块产品已有Git/测试：阶段来源分散优先接回现有任务/验收入口；只有现有系统确实无法表达或可靠更新状态，才比较增强任务机制。
- 多写者共同改权威状态：文字约定本身不能防止覆盖；比较单一受控写者与带版本前提/原子更新的入口，并验证冲突失败。暂停并发可以是有效较轻替代；不允许并发继续却只加README。
- 会覆盖重要真实数据：说明预览、权限范围和独立恢复为何必要；代码版本回退不是数据恢复。小脚本也不能因此降低保护。

这只是因果示例，不是固定推荐目录；依据当前事实与动作取舍。更重方案可等到明确的第二写者、外部暴露、真实重要数据或验证失败等变化，再评估。
