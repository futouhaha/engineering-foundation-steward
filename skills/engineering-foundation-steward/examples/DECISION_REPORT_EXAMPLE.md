## 用户方案

### 01 项目画像与信息充分性

建议先保住索引生成器的版本，再让失败的生成操作保留旧索引。本例是单人、离线、持续维护的虚构研究小工具。用户每次选一项工作，让一名助手实施和自查。现有资料足以判断本机首期；真实资料能否恢复、是否需要异地备份还待另验。

### 02 工程基建全景与适配结果

| 能力 | 依据 | 适配结果 |
|---|---|---|
| 目标、资料与程序分工 | README 指向 catalog.json，生成器据此写 INDEX | 已具备，可复用原入口 |
| 任务、许可、知识与交接 | 用户逐项定目标，决定沿用 README | 保留单写者；现在补验证入口与交回版本 |
| 版本、质量与操作失败恢复 | 目前只有旧回执，生成器直接覆盖 | 现在建立本地源码基线、拒写与失败测试 |
| 环境与协作 | 本地标准库，只有一个写者 | 目前无需新依赖、共享数据库或远端发布 |
| 资料备份 | 此次未验证 | 恢复能力未知；开始覆盖真实资料前再验 |

### 03 推荐建设方案与选择理由

本地 Git 能留住每次获准修改的源码和说明；手动复制很难让接手者找对测试对应的版本。第二项是在生成器内比较输入版本，先完整写临时输出，成功才替换旧索引。仅写“请小心”防不住写到一半的故障。初建需要一次源码盘点和一组虚构测试，此后每次改生成器复跑即可。单写者无需负担远端发布和多人审批的维护。

### 04 工程机制联动与实际使用方式

下一次用户要调整索引顺序时，先限定可改文件。助手读原说明与排序依据，核对提交和未提交改动，在副本上运行生成器，对照新顺序并复跑失败保护。获准才在 README 同步变更的规则；交回版本、实际输出及待决项，由用户接收。换人从同一入口重验，新的排序预期由当次目标确定。

### 05 工程成长与复评条件

Main 每次开工核写者与资料边界。若有第二个写者或开始覆盖真实文件，就在相关写入前请顾问复评冲突拒绝与独立备份恢复。跨设备接手时再核环境和异地版本。不假定已有自动提醒。

## 共同决定条款

### 06 本次批准范围、验收与退出

当前是提案。建议只允许一名 Main 在确认仓库归属后建立本地 .git，新增 .gitignore、tests/test_index.py，修改 tools/index.py 与 README.md。只收录这四份获准文件，测试使用临时虚构资料；保留原 catalog 和 INDEX，无联网、安装、费用或额外助手。

持续机制：每次改生成器都能找到对应源码版本，并从原入口检查正常生成及安全拒写。

下次复验：获准源码有可读取的本地提交；正常虚构输入生成预期索引；输入版本变化或写临时输出失败必须明确报错且旧输出逐字节不变。

建议最多两轮同范围返修，仍失败、出现并行编辑、需要扩权或用户叫停就停手保留差异，由用户结束或另批。只反向撤本次可辨认改动，重叠编辑先核对。删除新增文件另需许可。本地 Git 不能恢复已丢失的未跟踪研究资料。

## Main Brief

按 06 实施。起点是此示例快照中的单写者生成器。先读 README 与生成入口，核根仓库及父仓库归属、原调用和改前文件。只对获准清单保存源码基线，身份缺失时报用户。保留原命令与输出位置；用输入版本变化和临时写出失败检验旧索引保留。在临时目录对实际生成入口运行测试，用 `python3 -B -m unittest discover -s tests` 复跑并记录版本、输出与未验项。由 Main 在获准 README 记录方法，用户维护任务与接收决定。
